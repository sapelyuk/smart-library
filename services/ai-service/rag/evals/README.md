# evals — оценка качества RAG

> Здесь живёт **набор eval**: вопросы с заранее известными правильными ответами и правила, по которым
> они оцениваются. Прогон выполняет `scripts/eval-rag.ps1`. Этот файл объясняет, что означают цифры и
> почему пороги такие.

---

## 1. Зачем это нужно

Структурная проверка (`scripts/validate_workflow.py`) доказывает, что JSON workflow корректен. Smoke-тесты
доказывают, что точки входа отвечают. Ни то, ни другое не отвечает на единственный вопрос, который важен
пользователю: **хороши ли рекомендации**. Набор eval отвечает на него числом и падает, если изменение
незаметно ухудшило поиск (retrieval).

---

## 2. Как это работает

```
evals/rag-eval-suite.json          вопросы + ожидаемые книги   (единственный источник истины)
        |
        |  scripts/eval-rag.ps1
        v
   retrieve (по умолчанию)                    agent
   эмбеддинг вопроса -> косинусный            POST /webhook/book-rag/recommend,
   поиск по book_chunks (DISTINCT по книге)   оценка названных агентом книг
        |                                     |
        v                                     v
   precision@k, recall@k, hit@k, MRR  ->  пороги -> PASS/FAIL -> отчёт .md + .json
```

Два режима существуют потому, что они ломаются по-разному и стоят по-разному:

| | `retrieve` (по умолчанию) | `agent` |
|---|---|---|
| Что проверяет | качество поиска (вектор + индекс + эмбеддинги) | всю систему целиком, включая выбор инструментов моделью |
| Запросов к Gemini на вопрос | **1** (эмбеддинг) | ~3 (модель думает и вызывает инструменты) |
| Зависит от квоты чат-модели | нет | да |
| Детерминирован | да | нет (модель каждый раз может ответить иначе) |
| Где считается ответ | SQL-запрос, повторяющий поиск workflow | разбор текста ответа |

`retrieve` — это то, что можно гонять каждый день и после каждой правки порогов. `agent` — то, что
запускают перед деплоем, когда хочется знать, что конечный пользователь получит хороший ответ.

---

## 3. Определения метрик

Для вопроса с k (обычно 5) и множеством ожидаемых книг E:

| Метрика | Формула | Смысл |
|---|---|---|
| `precision@k` | `|найденные ∩ E| / |найденные|` | какая доля выданных книг оказалась нужной |
| `recall@k` | `|найденные ∩ E| / |E|` | какую долю ожидаемых книг удалось найти |
| `hit@k` | `1`, если найдена хотя бы одна ожидаемая книга, иначе `0` | нашлось ли хоть что-то |
| `MRR` | `1 / позиция первой ожидаемой книги` | насколько высоко стоит правильный ответ |
| `f1` | гармоническое среднее точности и полноты | одно число для точности и полноты сразу |

Три правила, без которых эти цифры вводили бы в заблуждение:

1. **Дубликаты удаляются до подсчёта.** Рекомендатель, который пять раз называет одну и ту же книгу, не
   должен выглядеть точным: `["dune", "dune"]` — это одна выданная книга, а не две.
2. **Деление — на число фактически выданных книг**, а не на k. Если поиск вернул 2 книги и обе нужны,
   `precision = 1.0`. Считать «из пяти» означало бы штрафовать за то, что в библиотеке мало книг.
3. **Неопределённые метрики — `null`, а не ноль.** У вопроса категории `refuse` (правильный ответ —
   не называть ничего) нет `recall`, `hit` и `MRR`. Они показываются как `-` и **исключаются** из
   средних, чтобы проверка отказа не искажала метрики поиска. Для такого вопроса действует только
   `precision`: назвал книгу — `0`, не назвал — `1`.

Итоговые (aggregate) числа — **макро-средние**: каждый вопрос весит одинаково, независимо от того,
сколько у него ожидаемых книг.

## 4. Формат набора

```json
{
  "suite": "book-rag-core",
  "version": 1,
  "defaults": { "k": 5, "category": "taste" },
  "questions": [
    {
      "id": "taste-after-dune",
      "category": "taste",
      "question": "I loved Dune - recommend something similar.",
      "expected": ["neuromancer-william-gibson", "left-hand-of-darkness", "the-city-and-the-city"],
      "also_mentions": ["dune-frank-herbert"],
      "note": "почему ожидается именно это"
    }
  ]
}
```

| Поле | Обязательно | Значение |
|---|---|---|
| `id` | да | уникальное, строчные буквы/цифры/дефисы; попадает в отчёт |
| `question` | да | то, что реально отправляется системе |
| `expected` | да | список `book_id`, которые должны быть найдены. **Пустой список = проверка отказа** |
| `category` | нет | `self`, `taste`, `genre`, `author`, `constraint`, `refuse` (по умолчанию `taste`) |
| `k` | нет | своё k для этого вопроса; иначе `defaults.k` |
| `also_mentions` | нет | книги, которые вопрос **сам** называет. Их упоминание в ответе не считается рекомендацией |
| `note` | нет | почему ожидается именно это; попадает в отчёт |

### Категории и их пороги

| Категория | Что проверяет | Порог |
|---|---|---|
| `self` | вопрос «Название книги» → эта же книга обязана найтись | `recall = 1.0` (жёстко, `-MinSelfRecall`) |
| `taste` | рекомендация по вкусу/настроению | общие пороги `-MinPrecision` / `-MinRecall` / `-MinHitRate` |
| `genre`, `author`, `constraint` | запрос по каталогу, автору, ограничению | общие пороги |
| `refuse` | в библиотеке ничего подходящего → агент **не должен** ничего выдумывать | `precision = 1.0` (`-MinRefusePrecision`) |

`self`-вопросы жёстче остальных намеренно: если система не находит книгу по её собственному названию,
сломан не вкус модели, а индекс, эмбеддинги или SQL-запрос. Это проверка работоспособности, а не качества.

`also_mentions` решает конкретную проблему: на вопрос `I loved Dune - recommend something similar.`
агент может ответить «Вы упомянули Dune, попробуйте Neuromancer». `Dune` здесь — эхо вопроса, а не
рекомендация, и без `also_mentions` такое эхо засчитывалось бы как попадание.

## 5. Запуск

```powershell
# 0. Офлайн: проверить сам набор. Ни docker, ни сети, ни ключа не нужно.
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1 -ValidateOnly

# 1. Обычный прогон: эмбеддинги + поиск. Один запрос к Gemini на вопрос.
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1

# 2. Перед деплоем: сквозная проверка через реальный webhook (дороже по квоте).
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1 -Mode agent

# 3. Строже/мягче: пороги задаются параметрами.
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1 -MinRecall 0.5 -K 3

# 4. Сделать удачный прогон эталоном для сравнения будущих.
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1 -PromoteBaseline

# 5. Пересчитать пороги по сохранённому прогону: без docker, без сети, без квоты.
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1 -InputResults .\evals\results\rag-eval-...json
```

Коды возврата: `0` — все пороги пройдены, `1` — что-то не прошло, `2` — ошибка вызова (нет набора,
нет нужного сервиса). Это позволяет встроить прогон в любой скрипт или CI.

| Параметр | По умолчанию | Значение |
|---|---|---|
| `-Mode` | `retrieve` | `retrieve`, `agent` или `both` |
| `-K` | из набора | переопределяет `defaults.k` (не трогает вопросы со своим `k`) |
| `-MinPrecision` | `0.40` | минимальная средняя точность (`0` отключает проверку) |
| `-MinRecall` | `0.60` | минимальная средняя полнота |
| `-MinHitRate` | `0.60` | минимальная доля вопросов с попаданием |
| `-MinSelfRecall` | `1.00` | точность на `self`-вопросах |
| `-MinRefusePrecision` | `1.00` | насколько строго наказывать выдумывание |
| `-MaxErrors` | `0` | допустимое число ошибок выполнения |
| `-MaxRegression` | `0.05` | допустимое падение относительно эталона |
| `-OutDir` | `evals\results` | куда писать отчёт (`0` — не писать) |
| `-Baseline` | `evals\baseline.json` | с чем сравнивать |
| `-InputResults` | — | пересчитать сохранённый прогон вместо новых запросов |
| `-PromoteBaseline` | выкл. | сохранить **успешный** живой прогон как эталон |

Пороги выбраны так, чтобы первый честный прогон был **проходимым, но не бесплатным**: они не
подгоняются под неизвестный результат. После первого прогона в [docs/PROGRESS.md](../docs/PROGRESS.md)
фиксируется факт: либо «прошло», либо «не прошло и вот почему», и порог меняется осознанно.

## 6. Как читать отчёт

`scripts/eval-rag.ps1` пишет два файла в `evals/results/`:

- `rag-eval-<время>-<режим>.json` — всё: пороги, метрики по вопросу, тексты ответов агента.
- `rag-eval-<время>-<режим>.md` — то же для чтения глазами: агрегаты по категориям, таблица порогов,
  таблица по вопросам и ответы агента целиком.

Отчёт — это артефакт, а не источник истины: источник истины — набор в `evals/rag-eval-suite.json`.

Пересчитать любой сохранённый прогон независимой реализацией метрик:

```powershell
& "C:\Users\ThinkPro\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe" `
    scripts\eval_metrics.py --results .\evals\results\rag-eval-....json --detail
```

`scripts/eval_metrics.py` считает те же метрики второй, независимой реализацией. Если числа
разойдутся, он скажет об этом и вернёт код `1`: значит, изменились правила подсчёта, а не библиотека.

## 7. Тесты самой оценки

Метрики — это код, и он тоже может быть неправильным. Эти тесты работают **офлайн**: без docker,
без сети, без ключа и без квоты.

```powershell
$py = "C:\Users\ThinkPro\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe"

# 53 теста: определения метрик, разбор названий, аудит набора, CLI, фикстуры
& $py -m unittest discover -s tests -t . -p "test_*.py" -v

# аудит набора и потолок каждой оценки (ничего не запускает)
& $py scripts\eval_metrics.py --audit --expected
```

Фикстуры в `evals/fixtures/` **синтетические**: ответы выводятся из ожидаемых книг самого набора,
поэтому они доказывают правила подсчёта, а не качество библиотеки. Пересоздать их:

```powershell
& $py tests\_make_fixtures.py
```

| Фикстура | Что это | Зачем |
|---|---|---|
| `perfect-run.json` | идеальный прогон | проверка, что верный ответ даёт PASS |
| `degraded-run.json` | прогон с реальными провалами | проверка, что пороги и отчёт ловят плохой результат |
| `agent-mode-run.json` | ответы прозой + одна намеренно испорченная строка | проверка разбора ответов агента |

Их можно прогнать через сам harness, не тратя ни одного запроса:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1 -InputResults .\evals\fixtures\degraded-run.json
```

## 8. Известные ограничения

Их лучше знать заранее, чем удивляться цифрам:

1. **Ограничения по числам не понимаются поиском (по векторам).** Запрос «что-нибудь короткое, меньше
   400 страниц» ранжируется по смыслу, а не по `page_count`. Вопрос `taste-short-and-funny` измеряет
   этот разрыв, а не притворяется, что его нет. Настоящее исправление — фильтр по метаданным, а не порог.
2. **`expected` — это суждение, а не истина в последней инстанции.** «Похоже на Dune» — вопрос вкуса.
   Список ожидаемых книг зафиксирован в наборе и обсуждаем; если он неверен, неверны и метрики.
3. **Один вопрос = одна оценка.** Макро-среднее по 21 вопросу — это шумная оценка: один вопрос меняет
   среднюю точность примерно на 0.05. Поэтому есть жёсткие пороги по категориям (`self`, `refuse`),
   а не только средние.
4. **Режим `agent` недетерминирован** и зависит от квоты; `retrieve` детерминирован и является
   основным ежедневным инструментом.
5. **Разбор ответов агента по названиям — эвристика.** Он ищет названия книг в тексте, и усечённое
   название он считает совпадением (см. `mentioned_books` в `scripts/eval_metrics.py`): «Sapiens»
   засчитывается как «Sapiens: A Brief History of Humankind». Побочный эффект — частичное название
   может совпасть слишком щедро. Для вопросов, где ложное попадание критично, в наборе спрашиваются
   полные названия.
6. **Вектор поиска не тот же самый код, что в workflow.** `retrieve` повторяет тот же запрос
   (`halfvec` + косинус + `DISTINCT ON` по книге) на той же таблице, но это отдельный SQL. Если
   изменится узел `Search Book Library` в workflow, режим `retrieve` этого не заметит — для этого
   нужен режим `agent`.

## 9. Как добавить вопрос

1. Выберите `book_id` из `samples/books.csv` (или из живой таблицы `books` — они совпадают).
2. Добавьте вопрос в `evals/rag-eval-suite.json`. Если вопрос называет книгу из каталога, добавьте её
   `book_id` в `also_mentions`.
3. Прогоните офлайн-проверку — она бесплатна и сразу скажет, если `book_id` не существует, если
   забыт `also_mentions`, если `expected` больше `k`, или если какие-то книги каталога вообще нигде
   не ожидаются:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1 -ValidateOnly
```

4. Только после этого тратьте запросы:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\eval-rag.ps1
```

Новый вопрос, добавленный в один день с провалом, — это не поломка, а результат: сначала записывается
факт, потом решается, менять модель, запрос или ожидание.
