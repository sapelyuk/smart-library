## 2. Правила работы с базой данных

1. Векторное хранилище живёт в своём **отдельном Docker-контейнере** (`pgvector/pgvector:pg17`), опубликованном на
   **порту хоста 5433**, никогда на 5432. Порт 5432 принадлежит существующему Postgres пользователя.
2. Имя контейнера фиксировано: `n8n-book-rag-db`. Имя тома фиксировано: `n8n_book_rag_pgdata`.
   Изменение любого из них ломает задокументированные команды; если изменение неизбежно, обнови SETUP.md,
   PROGRESS.md и этот файл в том же изменении.
3. Все изменения схемы идут в `db/01-schema.sql` и должны быть **идемпотентными**
   (`CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, `CREATE INDEX IF NOT EXISTS`).
   Это исправляет известный дефект в проанализированном шаблоне, который использовал голый `CREATE TABLE`.
   **Всегда применяй его с `-v ON_ERROR_STOP=1`** и следом запускай `scripts\verify-db.ps1`: psql останавливается на
   первой ошибке, поэтому сбой в середине файла оставляет наполовину построенную базу данных, которая всё ещё выглядит живой.
4. **Размерность эмбеддинга — это константа уровня схемы.** Она объявлена один раз в `db/01-schema.sql` и
   должна точно совпадать с выводом узла эмбеддингов. Эталонная цифра:
   - **EMBEDDING_DIM = 3072**, тип колонки **`halfvec(3072)`** (см. ADR-002 и ADR-005b)
   - `halfvec` **не** опционален: pgvector **не может построить HNSW-индекс по обычному `vector` выше 2000
     измерений**. Проверено на pgvector 0.8.7 — колонка обычного `vector(3072)` падает с ошибкой
     `column cannot have more than 2000 dimensions for hnsw index`.
   - Узел эмбеддингов Gemini в n8n не предоставляет **никакого управления размерностью вывода**, поэтому 3072 задано жёстко. Подтверди
     с помощью `scripts\check-embedding-dim.ps1` перед первой загрузкой.
5. **`book_chunks.book_id` должен оставаться nullable и НЕ должен иметь внешнего ключа.** Узел вставки PGVector в n8n
   записывает только `id`, `text`, `metadata`, `embedding`. Связь с книгой живёт в
   `metadata->>'book_id'`, а удаление книги идёт через функцию `delete_book()`. Не
   "улучшай" это, добавляя ограничение обратно — это ломает каждую загрузку.
6. Никогда не храни секреты в SQL-файлах, JSON workflow или документации. Данные подключения берутся из `.env`,
   который **игнорируется git**.
7. **Тестовые эмбеддинги должны быть ненулевыми.** Вектор из одних нулей имеет неопределённое косинусное расстояние, и
   HNSW-индекс не вернёт его, порождая вводящее в заблуждение "нет результатов". Это тратит время на отладку.

## 3. Правила работы с workflow

1. JSON workflow в `workflow/book-rag-system.json` — это **единственный источник истины**. Пользователь
   импортирует его в n8n; правки, сделанные в интерфейсе n8n, должны быть экспортированы обратно в этот файл, иначе они потеряны.
2. **Никаких инструментов SQL со свободным текстом в стиле `sql_query`.** LLM никогда не должен иметь возможности выдавать сырой SQL. Любой инструмент SQL
   должен использовать параметризованные запросы (`queryReplacement` / `$1`) со значениями, подставляемыми из `$fromAI`.
   *(Намеренное исправление критического дефекта инъекции, найденного в проанализированном шаблоне.)*
3. Каждый узел, который может упасть на плохом вводе — загрузка файла, извлечение текста, вызовы эмбеддингов — должен задавать
   `onError: "continueRegularOutput"` и разумный `retryOnFail`. Никаких молчаливых сбоев всего workflow.
4. Удаления должны происходить **после** успешного извлечения/эмбеддинга или быть ограничены областью так, чтобы сбой в середине
   конвейера не мог оставить библиотеку наполовину проиндексированной. Предпочитай "upsert, затем чистка" вместо "удалить, затем вставить".
5. Ключи метаданных вектора записываются **без** ведущего `=` и читаются с тем же написанием.
   *(Исправление дефекта `=file_id` в проанализированном шаблоне.)*
6. Выражения, ссылающиеся на текущий элемент цикла, должны использовать `$('Node').item.json.x`, **никогда**
   `$('Node').first().json.x`, внутри `Loop Over Items` / `Split In Batches`.
7. Учётные данные (credential) указываются в JSON workflow **только по имени**. Пользователь привязывает их в интерфейсе n8n.
   Никогда не коммить ID учётных данных (credential) из любого другого экземпляра.
8. `pinData` должен быть пустым в закоммиченном JSON. Тестовые фикстуры принадлежат `samples/`.

## 4. Правила документации

1. `docs/PROGRESS.md` обновляется в **конце каждой рабочей сессии**, даже если сессия дала только
   решения. Он всегда должен отвечать: *что работает, что дальше, что заблокировано.*
2. `docs/DECISIONS.md` — только для добавления. Никогда не переписывай там историю; заменяй новым ADR.
3. Любое отклонение между задокументированным планом и построенным артефактом должно быть записано в
   PROGRESS.md в разделе "Отклонения", а не тихо исправлено.
4. **Язык документации — русский.** Вся документация (`README.md`, `docs/*.md`) ведётся **на русском
   языке**: заголовки, абзацы, списки, ячейки таблиц, blockquote. Новые документы пишутся сразу
   по-русски, а не переводятся потом.
5. **Язык кода — английский.** Комментарии и любые пояснения внутри кода остаются **только на
   английском**: скрипты (`scripts/*.ps1`, `scripts/*.py`), SQL (`db/*.sql`), конфигурация
   (`docker-compose.yml`, `.env.example`, `.gitignore`) и артефакты n8n
   (`workflow/book-rag-system.json` — `notes` узлов и sticky notes). Кириллицы в этих файлах быть не
   должно.
6. **Что не переводится никогда** — ни в документации, ни в коде: имена файлов и пути, команды, имена
   узлов, функций и credential'ов, ключи и переменные окружения, HTTP-пути, заголовки, идентификаторы,
   числа, версии, порты, коды ошибок и имена моделей. При переводе документации блоки кода и inline-код
   переносятся **байт в байт**, включая английские комментарии внутри примеров кода.

## 5. Правила работы с моделями

1. **Конфигурация по умолчанию для работы — бесплатная.** Эмбеддинги на бесплатном тарифе Google Gemini; чат-модель
   агента на бесплатном плане Groq. Никогда не делай платный сервис жёсткой зависимостью. См. ADR-005a — бесплатный тариф Gemini
   Flash **не** достаточно велик, чтобы поддерживать агента с вызовом инструментов (~20 запросов/день ≈ одна
   беседа), поэтому чат и эмбеддинги — намеренно отдельные решения.
2. Слой моделей должен оставаться заменяемым: чат-модель и модель эмбеддингов каждая живёт ровно в одном
   узле, поэтому смена провайдера — это изменение одного узла (ADR-002, ADR-005a). Узел чат-модели агента
   называется `Chat Model (swap me)`.
3. Соблюдай лимиты запросов бесплатного тарифа во время массовой загрузки. Загружай пакетами (`Loop Over Books`, размер пакета 3)
   вместо того, чтобы отправлять каждый запрос сразу.
4. Агент должен быть проинструктирован **никогда не выдумывать книги**, которых нет в библиотеке. Если ничего
   не совпадает, он так и говорит. Эта инструкция живёт в системном сообщении агента и не должна быть удалена.
5. Квоты бесплатного тарифа **недолговечны** — они многократно менялись в течение 2026 года. Проверяй в консоли
   провайдера перед большой загрузкой, вместо того чтобы доверять любой цифре, написанной в этих документах.
6. Смена провайдера **эмбеддингов** делает недействительным каждый сохранённый вектор и требует полной переиндексации.
   Смена провайдера **чата** — нет. Не путай эти две вещи.

## 6. Правила безопасности

1. Точка входа `Webhook` использует аутентификацию по заголовку. Чат-триггер по умолчанию публичен в
   n8n; если экземпляр доступен за пределами localhost, сообщи об этом пользователю.
2. Инструменты базы данных агента по замыслу только для чтения. Выдай роли Postgres, используемой агентом,
   только `SELECT`, где это практически возможно.
3. `encryptionKey` экземпляра n8n в `C:\Users\ThinkPro\.n8n\config` никогда не должен копироваться в этот
   репозиторий или в документацию.
