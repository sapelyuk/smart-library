## ADR-001 — Использовать бесплатный тариф Google Gemini как поставщика модели по умолчанию

**Дата:** 2026-10-01
**Статус:** Принято
**Заменяет:** —

### Контекст
Пользователь спросил, покупать ли Google Gemini или подключить DeepSeek через API, и уточнил главное
ограничение: *начать без платежей*. Системе нужны две разные возможности моделей:

1. **чат-модель**, поддерживающая вызов инструментов, потому что узел n8n AI Agent — это агент, вызывающий инструменты;
2. **модель эмбеддингов**, используемая одинаково во время загрузки и во время запроса.

### Рассмотренные варианты

| Вариант | Нужна оплата | Вызов инструментов | Эмбеддинги | Вердикт |
|---|---|---|---|---|
| **Бесплатный тариф Google Gemini** (ключ AI Studio) | **Нет** — только аккаунт Google | Да | Да (тот же ключ) | **Выбрано** |
| DeepSeek API | Да — предоплата, минимальное пополнение | Да | **Нет** (только чат) | Отложено как улучшение |
| OpenAI | Да | Да | Да | Отклонено, пока цель — бесплатность |
| Ollama (локально) | Нет | Да | Да (`nomic-embed-text`) | Запасной вариант, если нужны офлайн/приватность |

Один DeepSeek не может удовлетворить требование, потому что у него нет эндпоинта эмбеддингов — всегда
понадобился бы второй поставщик для поиска (по векторам).

### Решение
Использовать **бесплатный тариф Google Gemini** и для чат-модели агента, и для эмбеддингов. DeepSeek остаётся
**задокументированной заменой одного узла** на будущее (сообщественный узел `n8n-nodes-deepseek` 1.0.6 уже
установлен).

### Последствия
- Нулевые денежные затраты на запуск системы.
- **Лимиты запросов** бесплатного тарифа — главный операционный риск, особенно при массовой загрузке множества
  книг → загрузка должна ограничивать темп (см. ADR-004).
- Бесплатные тарифы и идентификаторы моделей со временем меняются. Поэтому имя модели — это одно редактируемое значение
  на узел, и SETUP.md предлагает пользователю проверить актуальные идентификаторы моделей во время настройки.
- Если пользователь позже добавит средства на DeepSeek, изменится только узел чат-модели `Book Recommendation Agent`;
  эмбеддинги останутся на Gemini, чтобы существующий индекс остался действительным.
- **Не** смешивайте поставщиков эмбеддингов между загрузкой и запросом. Смена поставщика эмбеддингов
  делает недействительным каждый сохранённый вектор (см. ADR-002).

## ADR-002 — Размерность эмбеддингов зафиксирована на 1536, чат-модель и модель эмбеддингов изолированы в отдельных узлах

**Дата:** 2026-10-01
**Статус:** Принято

### Контекст
Проанализированный нами шаблон (`Ultimate_Agentic_RAG_AI_Agent_Template.json`) поставлялся с жёстко заданной
колонкой `vector(1536)` и двумя отдельными узлами эмбеддингов. Такая связанность делает модель эмбеддингов
фактически постоянной, а использование двух по-разному настроенных узлов эмбеддингов в одном workflow
молча испортило бы поиск (по векторам).

### Решение
1. `EMBEDDING_DIM = 1536` объявляется один раз в `db/01-schema.sql` и повторяется в этом журнале. Узел
   эмбеддингов должен быть настроен на выдачу ровно такого числа размерностей.
2. Ровно **один** узел эмбеддингов используется и для загрузки, и для поиска (по векторам), подключённый к обоим узлам
   векторного хранилища, поэтому два пути никогда не смогут разойтись. Приложение переиспользует его, а не дублирует.
3. Чат-модель находится ровно в одном узле, поэтому поставщика можно заменить в одном месте.

### Последствия
- Смена поставщика эмбеддингов требует изменения схемы и полной переиндексации — это задокументировано, а не
  выясняется на собственных ошибках.
- Векторный поиск использует **косинусное расстояние** (`vector_cosine_ops`, оператор `<=>`) — правильную
  метрику для нормализованных текстовых эмбеддингов.
- Создаётся индекс `ivfflat` с `lists = 100` для приближённого поиска ближайших соседей; этого достаточно для
  библиотеки в тысячи — десятки тысяч чанков. Для очень большой библиотеки переключитесь на
  HNSW (`USING hnsw (embedding vector_cosine_ops)`).

### Замечание о выборе размерности Gemini
Модели эмбеддингов Gemini могут выдавать несколько значений ширины. 1536 выбрана намеренно, потому что это
наиболее поддерживаемая ширина у всех поставщиков, к которым мы могли бы перейти, поэтому будущая смена поставщика
сама по себе не вынуждает менять схему.

## ADR-003 — Выделенный Docker-контейнер pgvector на порту хоста 5433

**Дата:** 2026-10-01
**Статус:** Принято

### Контекст
У пользователя уже локально работает Postgres, **и** есть Docker. Отсюда следуют два ограничения: существующий
Postgres нельзя затрагивать, и расширение для векторов должно присутствовать.

### Рассмотренные варианты
| Вариант | Риск |
|---|---|
| Установить `pgvector` в существующий Postgres пользователя | Изменяет базу данных, на которую пользователь полагается; `pgvector` должен быть доступен для его точной версии и способа установки |
| **Выделенный контейнер на порту 5433** | **Выбрано** — полностью изолирован, воспроизводим |
| Supabase | Добавляет зависимость от облака и противоречит цели нулевой стоимости |

### Решение
Запустить `pgvector/pgvector:pg17` как контейнер `n8n-book-rag-db` с томом `n8n_book_rag_pgdata`,
опубликованным на **5433:5432**. Собственный Postgres пользователя на 5432 никогда не затрагивается.

### Последствия
- Запуск — одна команда (`scripts\start-db.ps1`), а остановка неразрушающая
  (`docker compose down` сохраняет том).
- Данные переживают пересоздание контейнера благодаря именованному тому; уничтожает их только `down -v`, и это
  намеренно не обёрнуто в скрипт.
- Учётные данные (credential) Postgres для n8n должны указывать на `localhost:5433`.
- Docker Desktop должен быть запущен; если демон не работает, compose завершается ошибкой — скрипт запуска это проверяет.

## ADR-004 — Два пути загрузки: массовое сканирование папки и webhook для одного файла

**Дата:** 2026-10-01
**Статус:** Принято

### Контекст
Пользователь выбрал «массовую загрузку из локальной папки плюс загрузку одного файла через webhook».

### Решение
- **Массовая загрузка / переиндексация:** ручной триггер читает папку с файлами каталога (`samples/books.csv` или
  собственные PDF/EPUB пользователя), обрабатывает элементы небольшими пакетами через `Loop Over Items`, чтобы соблюдать
  лимиты запросов бесплатного тарифа, и выполняет upsert в таблицу векторов.
- **Один файл:** `POST` в webhook с одной книгой. Тот же последующий путь нормализация → чанк → эмбеддинг → upsert,
  что и в массовом потоке, поэтому путь кода индексации один, а не два.
- Загрузка **идемпотентна**: повторная индексация той же книги заменяет её строки, а не дублирует их,
  с ключом по `book_id` (+ индекс чанка). Это намеренное улучшение по сравнению с проанализированным шаблоном,
  который удалял строки *перед* их повторной вставкой и потому мог уничтожить данные при сбое в середине запуска.

### Последствия
- Повторный запуск загрузки всегда безопасен.
- Массовой загрузке нужно ограничение темпа; workflow ждёт между пакетами, а не запускает всё сразу.
- В сборке по умолчанию нет зависимости от Google Drive. Загрузку по триггеру Drive можно добавить позже как
  необязательную ветку; она задокументирована как будущее расширение, но не реализована, потому что требует от пользователя
  настроить Google OAuth.

## ADR-005a — Разделить поставщиков: Gemini для эмбеддингов, Groq для агента (бесплатного тарифа Gemini Flash слишком мало для вызова инструментов)

**Дата:** 2026-10-02
**Статус:** Принято
**Заменяет (частично):** ADR-001 — предположение «один ключ делает всё» не выдержало проверки измерениями.
### Контекст
ADR-001 выбрал бесплатный тариф Gemini и для чата, и для эмбеддингов, исходя из того, что одни бесплатные
учётные данные (credential) покрывают и то и другое. Это рассуждение было верным насчёт *покрытия*, но ошибочным насчёт *ёмкости*.

Изучение текущих лимитов бесплатного тарифа (Google больше их не публикует; приведённые ниже цифры взяты
из тел ошибок квоты 429 и собственной документации Google) показало:

- Бесплатный тариф Gemini Flash: порядка **5 запросов в минуту и ~20 запросов в день** на проект.
- Агент n8n с вызовом инструментов тратит **несколько запросов на один ответ** (по одному на каждый вызов инструмента плюс по одному на
  каждый шаг генерации). Таким образом, ~20 запросов в день — это примерно **один разговор в день**.
- Задержка бесплатного тарифа под нагрузкой измерялась в десятках — сотнях секунд.
- **Эмбеддинги** Gemini гораздо щедрее (порядка 100 запросов в минуту, 1000 в день) и составляют
  основную часть работы при загрузке RAG.

### Решение
Использовать **два** поставщика, каждый для того, в чём он действительно хорош:

| Роль | Поставщик | Почему |
|---|---|---|
| Эмбеддинги | **Google Gemini** (`models/gemini-embedding-001`, бесплатный тариф) | Щедрая бесплатная квота; без банковской карты; один ключ |
| Чат-модель агента | **Groq**, бесплатный план (совместим с OpenAI) | ~30 запросов/мин, ~1000/день — рабочая бесплатная квота для цикла агента |

Gemini остаётся допустимым выбором для чат-модели при **лёгком, ручном** использовании; он просто не рассчитан
на агента, вызывающего инструменты. Переключение между ними — это **изменение одного узла**: `Chat Model (swap me)`.

DeepSeek по-прежнему остаётся естественным первым *платным* улучшением (дешёвый, совместим с OpenAI, поддерживает
вызовы инструментов) и не требует менять эмбеддинги.

### Последствия
- Двое учётных данных (credential) вместо одних: `Google Gemini (Book RAG)` для эмбеддингов и ключ Groq для чата.
  И те и другие по-прежнему можно получить бесплатно.
- **Поставщика эмбеддингов нельзя менять без необходимости.** Смена моделей эмбеддингов делает недействительным
  каждый сохранённый вектор (см. ADR-002) — эмбеддинги и чат — независимые решения, и именно поэтому
  их разделение безопасно.
- Бесплатные тарифы существенно менялись четыре раза в течение 2026 года (четыре поставщика полностью отказались от
  бесплатных предложений). Относитесь к любой конкретной квоте как к скоропортящейся и проверяйте её в консоли поставщика перед массовой загрузкой.

## ADR-005b — Столбец `book_chunks.embedding` имеет тип `halfvec(3072)`, и таблица чанков не имеет внешнего ключа

**Дата:** 2026-10-02
**Статус:** Принято
**Уточняет:** ADR-002

### Контекст
Два факта об интеграции были обнаружены при тестировании на реальном контейнере, а не при чтении документации:

1. **pgvector 0.8.7 отказывается создавать HNSW-индекс для обычной колонки `vector` размерностью выше 2000.** Применение
   первоначальной версии схемы завершилось ошибкой
   `ERROR: column cannot have more than 2000 dimensions for hnsw index`. Поскольку `psql` останавливается на этом
   месте в скрипте инициализации, сбой также молча пропустил все последующие инструкции, оставив
   функции несозданными — база данных выглядела наполовину подготовленной.
2. **Узел вставки PGVector Store в n8n записывает только `id`, `text`, `metadata`, `embedding`.** Он никогда
   не передаёт `book_id`, поэтому объявление `book_id NOT NULL` (или внешний ключ) приводит к сбою каждой вставки.

### Решение
1. Колонка имеет тип **`halfvec(3072)`**, с HNSW-индексом, использующим `halfvec_cosine_ops`. `halfvec` хранит 2
   байта на размерность вместо 4 и поддерживает до 4000 размерностей, поэтому индекс допустим, а
   хранилище сокращается примерно до 6 КБ на чанк. n8n по-прежнему отправляет обычный вектор; PostgreSQL его приводит.
2. В `book_chunks` столбец `book_id` остаётся **допускающим NULL и без внешнего ключа**. Авторитетная связь с книгой —
   **`metadata->>'book_id'`**, именно туда её помещает загрузчик документов workflow.
3. Поэтому идемпотентная переиндексация выполняется явно, а не за счёт ограничений: workflow выполняет
   параметризованный `DELETE FROM book_chunks WHERE metadata->>'book_id' = $1` перед повторной вставкой.
4. Удаление книги проходит через функцию `delete_book(book_id)`, которая удаляет строку каталога
   **и** его чанки вместе, потому что база данных больше не может выполнить каскад за нас.

### Последствия
- Поиск по сходству действительно использует индекс — подтверждено с помощью `EXPLAIN`: `Index Scan using
  book_chunks_embedding_idx`. Без `halfvec` это было бы в лучшем случае последовательное сканирование, а то и вовсе
  отсутствие создания таблицы.
- **Тестовые эмбеддинги должны быть ненулевыми.** У полностью нулевого вектора косинусное расстояние не определено, и
  HNSW-индекс его не вернёт (последовательное сканирование вернуло бы), из-за чего возникает путаница «нет результатов»,
  когда данные на самом деле есть. Это стоило одного цикла отладки, и поэтому `db/99-smoke-test.sql` это документирует.
- Осиротевшие чанки возможны, если строку удаляют из `books` в обход `delete_book()`. Запрос очистки
  находится в конце `db/01-schema.sql`.
- Любой, кто «приберётся» в схеме, вернув внешний ключ, сломает загрузку. Комментарий над
  таблицей говорит об этом прямо.

## ADR-005 — Инструменты агента параметризованы; инструмента с сырым SQL нет никогда

**Дата:** 2026-10-01
**Статус:** Принято

### Контекст
В проанализированном шаблоне был инструмент `Query Document Rows`, тело запроса которого было
`{{ $fromAI('sql_query') }}` — произвольный SQL, написанный моделью и выполняемый к базе данных пользователя. Это
уязвимость класса удалённого выполнения кода/`DROP TABLE`, достижимая из точек входа чата и webhook.

### Решение
Агент по книгам получает **четыре** инструмента, все параметризованные:

1. **`Search Book Library`** — векторный поиск по сходству по содержимому книг (основной инструмент RAG,
   режим `retrieve-as-tool`).
2. **`Get Book Details`** — точный поиск метаданных по одному `book_id` (вызывает `get_book($1)`).
3. **`List Library`** — просмотр/поиск по каталогу по одному термину свободного текста (вызывает `list_books($1, 25, 0)`).
4. **`Remove Book`** — единственный изменяющий инструмент; вызывает `delete_book($1)`, который атомарно удаляет строку каталога
   и его чанки. Это намеренно *узкая, именованная операция*, а не открытый SQL, и
   узел можно просто отключить, если агент не должен иметь возможности что-либо удалять.

Ни один инструмент не принимает SQL в виде свободного текста. Обоснование рекомендации («почему вам это понравится») выполняет
LLM по извлечённым строкам, а не SQL.

### Последствия
- Поверхность для инъекций из проанализированного шаблона полностью устранена.
- На некоторые аналитические вопросы, на которые ответил бы сырой SQL («среднее число страниц французских романов»), нельзя
  ответить напрямую; их можно добавить позже как *конкретный, параметризованный* инструмент, но никогда как открытый SQL.
- `list_books` намеренно принимает **один** аргумент: полагаться на то, что модель передаст несколько аргументов `$fromAI`
  в заданном порядке, ненадёжно, поэтому одно поле нестрогого совпадения заменяет отдельные фильтры по жанру и автору.
  Функция сопоставляет по названию, автору, жанру, тегам и описанию.
- Предоставление роли Postgres агента только прав `SELECT` остаётся рекомендуемой эшелонированной защитой;
  `bookrag_readonly` в `db/01-schema.sql` — это та самая роль, и ей **не** выдано право на `delete_book`.

## ADR-006 — Качество поиска измеряется набором eval с precision@k/recall@k, а не оценивается на глаз

**Дата:** 2026-10-02
**Статус:** Принято

### Контекст
К этому моменту проект умел доказывать две вещи: JSON workflow структурно корректен
(`scripts/validate_workflow.py`) и обе точки входа отвечают (`scripts/ingest-catalogue.ps1`, дымовые
тесты). Ни одна из них не отвечает на вопрос, ради которого система существует: **хороши ли
рекомендации**. Более того, в сессии 4b шесть дефектов потока данных прошли структурную проверку
незамеченными — то есть «валидатор зелёный» ничего не говорит о качестве.

Замена модели эмбеддингов, размера чанка, размера пакета или части системного промпта меняет качество
поиска, и без измерения это изменение невозможно отличить от шума. Бесплатная квота Gemini при этом
мала (~20 запросов в день на чат-модель), поэтому измерение обязано быть дешёвым.

### Решение
1. **Набор eval в репозитории**: `evals/rag-eval-suite.json` — вопросы с заранее известными
   `book_id`-ответами. Это данные, а не код: добавить вопрос не требует правки скриптов.
2. **Два режима прогона.** `retrieve` (по умолчанию) считает один эмбеддинг на вопрос и ранжирует
   библиотеку тем же косинусным поиском, что и workflow, — детерминированно и по цене одного запроса
   на вопрос. `agent` идёт через реальный `/webhook/book-rag/recommend` и оценивает книги, которые
   агент **назвал**, — это сквозная проверка, и её запускают перед деплоем.
3. **Метрики — precision@k, recall@k, hit@k и MRR**, макро-средние по вопросам. Дубликаты удаляются
   до подсчёта; неопределённые метрики (у вопросов категории `refuse`) не считаются нулями, а
   исключаются из средних. Определения зафиксированы в [evals/README.md](../evals/README.md).
4. **Пороги — это проверка (gate), а не отчёт.** Прогон возвращает код `0`/`1`, поэтому его можно
   встроить в скрипт деплоя. Жёсткие пороги стоят там, где ошибка означает поломку, а не вкус:
   `self`-вопросы требуют `recall = 1.0`, `refuse` — `precision = 1.0`.
5. **Сравнение с эталоном.** `-PromoteBaseline` сохраняет успешный прогон, и последующие прогоны
   сообщают о падении метрик больше `-MaxRegression` (по умолчанию 0.05) как о регрессии.
6. **Проверяемость без сети.** `-ValidateOnly` проверяет сам набор офлайн; `-InputResults` пересчитывает
   пороги по сохранённому прогону; `tests/test_eval_metrics.py` (53 теста) и синтетические фикстуры в
   `evals/fixtures/` доказывают правила подсчёта без единого запроса к API. `scripts/eval_metrics.py` —
   вторая, независимая реализация тех же метрик.

### Последствия
- Появился способ ответить «стало лучше или хуже» одним числом, и он дешёвый: полный прогон
  `retrieve` стоит 21 эмбеддинг и не трогает квоту чат-модели.
- **Список ожидаемых книг — это суждение, и оно теперь зафиксировано в репозитории.** Если суждение
  неверно, неверны и метрики; поэтому у каждого вопроса есть поле `note` с обоснованием, а изменения
  набора видны в истории.
- **Известные ограничения задокументированы, а не спрятаны**: поиск (по векторам) не понимает
  ограничений по числам (число страниц), режим `agent` недетерминирован, а разбор названий в ответе —
  эвристика. См. раздел «Известные ограничения» в [evals/README.md](../evals/README.md).
- `retrieve` повторяет поиск отдельным SQL-запросом, а не вызывает узел workflow. Это осознанный
  компромисс: так проверка не зависит от запущенного n8n. Расхождение с реальным узлом ловит режим
  `agent`, и это записано как ограничение.
- Пороговые значения по умолчанию (0.40 / 0.60 / 0.60) — **гипотеза до первого честного прогона**.
  Они не подгонялись под неизвестный результат; после первого прогона факт фиксируется в PROGRESS.md,
  и порог меняется осознанно, а не «чтобы стало зелёным».
