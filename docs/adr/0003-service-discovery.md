# ADR-0003. Обнаружение сервисов (Service Discovery)

- **Статус:** принято
- **Дата:** 2026-10-06
- **Задача:** #8

## Контекст

Сервисы Smart Library общаются синхронно через gRPC и асинхронно через RabbitMQ.
Для синхронных вызовов (например, API Gateway → User Service, Loan Service → Book Service)
каждому вызывающему нужно знать, где находится вызываемый сервис.

В Docker Compose DNS работает из коробки: контейнер `loan-service` подключается к
`book-service:8081` по имени сервиса — это уже проверяемый факт. Однако для
продакшн-развёртывания нужен единый механизм, который работает и локально, и в кластере.

## Рассмотренные варианты

- **Consul** — отдельный сервис-каталог с healthchecks, KV-хранилищем и UI.
- **Kubernetes DNS** — встроенный DNS-сервер кластера, автоматически создаёт записи
  для каждого `Service`-объекта.
- **Статическая конфигурация** — адреса сервисов задаются env-переменными или конфиг-файлом.
- **Docker Compose DNS** — работает локально, но не переносится на продакшн.

## Критерии выбора

1. Простота для локальной разработки.
2. Поддержка продакшн-развёртывания.
3. Интеграция с Kubernetes (де-факто стандарт для продуктовых микросервисов).
4. Минимальная операционная нагрузка.

## Решение

**Kubernetes DNS** как основной механизм обнаружения.

Локальная разработка использует **Docker Compose DNS** (уже работает).
Продакшн развёртывается в **Kubernetes**, где DNS создаётся автоматически
на основе `Service`-объектов.

Ниже описаны оба сценария.

### Локальная разработка: Docker Compose DNS

Сервисы в `docker-compose.yml` уже видят друг друга по имени контейнера:

```yaml
# loan-service (когда появится)
environment:
  BOOK_SERVICE_GRPC_ADDR: "book-service:8081"
  USER_SERVICE_GRPC_ADDR: "user-service:8082"
```

Docker Compose автоматически настраивает внутреннюю DNS-сеть:
`book-service` → `library-book-service` (по `container_name`).

Никаких дополнительных зависимостей не требуется.

### Продакшн: Kubernetes DNS

В Kubernetes каждый сервис описывается `Service`-объектом. DNS-сервер кластера
автоматически создаёт записи:

```
book-service.default.svc.cluster.local   → 10.96.0.15:8081
user-service.default.svc.cluster.local   → 10.96.0.16:8082
loan-service.default.svc.cluster.local   → 10.96.0.17:8083
```

Для вызова между сервисами достаточно использовать короткое имя:

```yaml
# ConfigMap или Deployment
env:
  - name: BOOK_SERVICE_GRPC_ADDR
    value: "book-service:8081"
```

Kubernetes DNS разрешает `book-service:8081` в IP-адрес pod'а.

## Обоснование

| Критерий | Consul | Kubernetes DNS | Статическая конфигурация |
| --- | --- | --- | --- |
| Локальная разработка | нужен дополнительный контейнер | **уже работает** в Docker Compose | работает, но хрупко |
| Продакшн | отдельная инфраструктура | **встроен в K8s** | требует внешнего механизма |
| Интеграция с K8s | через ExternalDNS или sidecar | **нативно** | не применимо |
| Операционная нагрузка | +1 сервис, бэкапы, обновления | **ноль** (управляет K8s) | ручное обновление конфигов |
| Healthchecks | встроенные проверки | **через ReadinessProbe** | нет |

**Kubernetes DNS** покрывает оба сценария без дополнительных зависимостей.
Docker Compose DNS работает локально "из коробки", Kubernetes DNS — для продакшена.

Consul добавляет инфраструктурную нагрузку (отдельный контейнер, KV-хранилище,
дополнительные healthchecks) без явной пользы, так как K8s уже предоставляет
встроенный DNS с автоматическим обновлением записей при масштабировании и rolling update.

Статическая конфигурация хрупка: при масштабировании или пересоздании pod'ов
IP-адреса меняются, и конфигурацию нужно обновлять вручную. Это не масштабируется.

## Архитектура сервисов

Продуктовый стек включает шесть сервисов, каждый из которых может вызывать другие:

| Сервис | Порт gRPC | Зависимости |
| --- | --- | --- |
| API Gateway | 8080 | User, Book, Loan, AI |
| Book Service | 8081 | (нет внешних) |
| User Service | 8082 | (нет внешних) |
| Loan Service | 8083 | Book, User |
| Notification Service | 8084 | User, Loan |
| AI Service | 8085 | Book |

### Зоны ответственности

- **API Gateway** — единая точка входа для клиентов (браузер, мобильное приложение).
  Маршрутизирует запросы к соответствующим сервисам, проверяет аутентификацию.
- **Book Service** — каталог книг, экземпляры. Самодостаточный.
- **User Service** — пользователи, роли, сессии. Самодостаточный.
- **Loan Service** — выдача/возврат, проверка прав через User Service, обновление
  статуса книги через Book Service.
- **Notification Service** — email/SMS уведомления. Подписывается на события
  RabbitMQ (`loan.overdue`, `book.borrowed`), запрашивает данные у User/Loan сервисов.
- **AI Service** — рекомендации. Запрашивает метаданные книг через Book Service
  для формирования контекста RAG.

### Механизм вызовов

Все межсервисные вызовы — синхронные gRPC. discovery решается через DNS:

```go
// Пример: loan-service подключается к book-service
conn, err := grpc.DialContext(ctx, "book-service:8081",
    grpc.WithTransportCredentials(insecure.NewCredentials()),
)
```

В Kubernetes `book-service:8081` разрешается автоматически.
В Docker Compose то же самое работает по имени контейнера.

## Последствия

### Положительные

- **Ноль дополнительных зависимостей.** Не нужно разворачивать Consul, Etcd или другой каталог.
- **Единый механизм.** Docker Compose DNS и Kubernetes DNS используют одинаковый
  подход: DNS-имя = имя сервиса. Конфигурация env-переменных не меняется при переходе.
- **Автоматическое обновление.** При масштабировании или rolling update Kubernetes
  автоматически обновляет DNS-записи. Docker Compose делает то же локально.
- **Healthchecks.** Kubernetes ReadinessProbe блокирует трафик от неготовых pod'ов.
  Docker Compose healthcheck (`depends_on.condition: service_healthy`) обеспечивает
  аналогичное поведение локально.

### Отрицательные / ограничения

- **Требует Kubernetes для продакшена.** Если кластер недоступен, нужен fallback
  на ручное управление (например, через статические IP в production-файлах).
- **Локальная разработка ограничена.** Docker Compose DNS работает только для сервисов,
  запущенных в одном compose-файле. Для тестирования с хост-машиной нужно пробрасывать
  порты (уже реализовано через `ports:` в docker-compose.yml).

### Не снимается выбором discovery

- Межсервисные вызовы требуют авторизации (bearer-токены, мTLS). Discovery не решает
  вопросы безопасности — это отдельная задача (mTLS, SPIFFE/SPIRE).
- Discovery не заменяет load balancing. Kubernetes Service обеспечивает базовый
  round-robin; для продвинутого (canary, weighted) нужен Ingress-контроллер или
  service mesh (Istio, Linkerd).
