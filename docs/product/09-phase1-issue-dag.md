# План задач Phase 1: граф зависимостей

Документ фиксирует Decomposition Phase 1 на атомарные задачи, порядок их выполнения и границы скоупа. Тела задач живут в GitHub Issues (номера в таблице ниже); здесь — только зависимости и обоснование границ, потому что эти сведения нужны при планировании и не видны из отдельного issue.

## Метки в GitHub

| Метка | Смысл |
| --- | --- |
| `phase1a` | Читательский путь: каталог, поиск, wishlist, рейтинги, сигналы, оба фронтенда, e2e |
| `phase1b` | Каналы доставки и защита: Telegram, Mailpit/e-mail, проверка rate limiting |

Phase 1 разбит на две подфазы, потому что итоговый набор превысил 15 задач, а `phase1b` не блокирует exit criteria читательского пути.

## Критический путь к exit criteria Phase 1

`#89 → #90 → #91 → #92` (конвейер сигналов) параллельно с `#96 → #97/#98 → #99/#100 → #101` (фронтенды) и `#93`, `#94` (AI), замыкается в `#102` (e2e).

`phase1b` (#103–#106) на критический путь не влияет и может выполняться параллельно или сдвигаться.

## Параллельность

Одновременно без конфликтов файлов можно выполнять:

- **#89, #93, #94, #95, #96, #103, #105** — старт без ожиданий, разные модули.
- **#97 и #98** — разные каталоги (`services/frontend-web/`, `services/frontend-app/`), конфликтуют только через `docker-compose.yml` и `go.work`: правки в них — отдельным коммитом, по одной задаче за раз.
- **#90 и #91** — оба меняют `book.proto` и `internal/handler/grpc.go`: выполнять последовательно или согласовать порядок слияния PR.

## Отклонения от продуктовых документов

Зафиксированы в телах соответствующих issues, здесь — сводка:

1. **`Search` и `ListSimilarBooks` перенесены в `ai.v1.AiService`** (#93), а не в `book.v1.BookService`, как в [`05-api-additions.md`](./05-api-additions.md). Причина: pgvector принадлежит ai-service; чтение чужой БД нарушает database-per-service, а вызов ai-service из book-service создал бы циклическую зависимость Go-модулей. PR #93 обязан синхронизировать `05-api-additions.md`.
2. **Telegram перенесён из Phase 2 в Phase 1b** (#103, #104) по решению владельца продукта. В [`02-roadmap.md`](./02-roadmap.md) останется пометка о переносе.
3. **Rate limiting не реализуется заново** (#106): он уже работает в `services/user-service/internal/handler/ratelimit.go` (задача #34). Задача — проверить поведение через gateway и задокументировать пороги.

## Вне скоупа Phase 1

| Элемент | Причина | Куда отнесён |
| --- | --- | --- |
| Книжные клубы | Нет исследования потребностей куратора, нет UX-макета | Phase 2 |
| Персонализация (collaborative filtering) | Нет накопленных сигналов — нужен отработавший Phase 1 | Phase 2 |
| Платежи (ЮKassa/Тинькофф) | Нет подтверждённой бизнес-модели и платящего сегмента | Phase 3 |
| Очередь ожидания (hold queue) | Нет метрики спроса и пиковых нагрузок | Phase 3 |
| Row-Level Security | В Phase 1 один tenant с фиксированным UUID | Phase 3 |
| `tenant_id` в `books`, `users`, `loans` | Миграция затрагивает все сервисы сразу; в Phase 1 tenant статический | Phase 3 |
| Elasticsearch / внешний полнотекстовый движок | `pgvector` + `to_tsvector('russian')` достаточно для каталога района | Phase 2+ при росте каталога |
| Web push | Нет установленной PWA-базы пользователей | Phase 2+ |
| A/B-тестирование | Нет трафика для статистической значимости | Phase 2+ |
| Выдача данных по запросу (152-ФЗ/GDPR) | Нет реальных персональных данных в Phase 1 | Phase 2 |
