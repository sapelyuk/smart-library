# 07. Non-Goals and Risks

## Anti-Scope (Non-Goals)

Это то, что мы **сознательно не делаем**. Каждый пункт — не «потом», а «не в рамках текущей стратегии».

| Non-goal | Обоснование | Когда пересматривается |
| --- | --- | --- |
| **Нативное мобильное приложение** | PWA (frontend-app) покрывает 90% use-cases. Нативное — +2 команды (iOS/Android), +2 магазина, +2 цикла релизов. ROI не оправдан для публичной библиотеки. | Никогда, пока PWA не упрётся в ограничение (push-уведомления, offline-first). |
| **Соцсеть «для всех читателей»** | Мы строим B2B2C: клубы при библиотеках, а не «Facebook для книголюбов». Соцсеть требует модерации в масштабе, репорт-системы, алгоритмической ленты. | Никогда. Это отдельный продукт. |
| **Универсальная библиотечная система (vs Koha)** | Koha, ИРБИС, МАРК-SQL — полные АИБС: каталогизация MARC, МБА, статистика по ГОСТ. Мы — AI-слой поверх (или вместо) АИБС, а не замена. | Никогда. |
| **Аудиокниги / ридер** | Не наша компетенция. Читатель слушает в Яндекс.Музыке/Storytel, а у нас — каталог бумажных книг и клубы. | Никогда. |
| **Ранняя монетизация AI-фич** | AI-компаньон бесплатен для читателя. Монетизация — через SaaS-подписку библиотеки. Freemium для читателя — не ранее Phase 3 и только после валидации. | Phase 3+, при наличии платящих B2B-клиентов. |
| **Schema-per-tenant** | 20 библиотек × 5 сервисов × 10 таблиц = 1000 схем. Сложность миграций, бэкапов, мониторинга неоправданна для масштаба 5–20 библиотек. | Никогда при текущем масштабе. |
| **Database-per-tenant** | 20 библиотек × 5 сервисов = 100 PostgreSQL-экземпляров. Операционная нагрузка избыточна. | Никогда при текущем масштабе. |
| **LMS-интеграции (Moodle, МЭО, 1С:Библиотека)** | Школьный/вузовский сегмент — Phase 2–3. Требует отдельных ADR, группового входа, привязки к учебной программе. | Phase 2–3, при наличии платящих клиентов из этого сегмента. |
| **SSO (LDAP/SAML)** | Корпоративный сегмент — Phase 3+. Публичная библиотека не требует SSO. | Phase 3+. |
| **AI-модерация контента** | Базовая модерация (жалоба → библиотекарь) достаточна для пилота. AI-модерация — Phase 3, требует обучения, false-positive анализа. | Phase 3. |

## Риски и митигации

### R1. Cold start рекомендаций

**Что:** Новый читатель не имеет истории. Рекомендации «на основе того, что вы читали» невозможны.

**Вероятность:** Высокая (все новые читатели).

**Влияние:** Высокое — первый опыт = пустые рекомендации → отток.

**Митигации:**

| Фаза | Митигация |
| --- | --- |
| Phase 1 | Ручные подборки библиотекаря: «Книга месяца», «Что читать по настроению» (seed-контент). Семантический поиск работает без истории. |
| Phase 1 | Онбординг: «Выберите 3 книги, которые вам понравились» → cold start с 3 сигналов. |
| Phase 2 | Персонализация на истории выдач (loan-service) — не требует AI-сессий. |
| Phase 3 | Импорт из Goodreads/LiveLib: читатель импортирует историю → мгновенный cold start. |

**Что НЕ делаем:** Не покупаем сторонние рекомендательные датасеты (MovieLens-подобные для книг не существуют в русском сегменте).

---

### R2. Приватность читателя

**Что:** Платформа собирает историю чтения, оценки, AI-сессии. Это чувствительные данные.

**Вероятность:** Средняя (риск не в утечке, а в неправильном использовании).

**Влияние:** Критическое — 152-ФЗ, потеря доверия библиотеки.

**Митигации:**

| Митигация | Где |
| --- | --- |
| PII (email, ФИО, телефон) не попадает в LLM-контекст | `06-signals-and-analytics.md`, раздел «Приватность» |
| `reader_id` в AI-контексте заменяется на хеш | `ai-service/internal/service/` (при сборке контекста) |
| Opt-in для клубов: вступление = явное действие | `JoinClub` (authenticated, `05-api-additions.md`) |
| `signal_events` — append-only, не удаляется автоматически | `04-data-model.md` |
| Экспорт данных по запросу (152-ФЗ) | Phase 3 |
| Шифрование при передаче (TLS) | Phase 3 (ingress в K8s) |
| Хранение токенов только как SHA-256 hash | `services/user-service/migrations/001_init.sql` (уже реализовано) |

**Open question:** Нужен ли DPO (Data Protection Officer) для пилота? Для 5–20 библиотек с обезличенными сигналами — скорее нет, но юридическая проверка нужна.

---

### R3. Vendor lock-in на n8n

**Что:** AI-сервис вызывает n8n webhook для генерации рекомендаций. n8n — low-code, его замена требует переписывания workflow.

**Вероятность:** Средняя (n8n может измениться, квоты Gemini закончатся, production-требования вырастут).

**Влияние:** Среднее — контракт `ai.v1.AiService` не изменится, но внутренняя реализация потребует переписывания.

**Митигации:**

| Митигация | Где |
| --- | --- |
| n8n инкапсулирован за `internal/n8n/client.go` | `services/ai-service/internal/n8n/` |
| Контракт `ai.v1.AiService` не зависит от n8n | `services/ai-service/proto/ai/v1/ai.proto` |
| Вариант C (нативный Go-порт RAG) — ADR-0002, задокументированное направление | `docs/adr/0002-ai-recommendation-architecture.md` |
| Eval-набор (`evals/`) позволяет сравнить качество при замене | `services/ai-service/rag/evals/` |
| Dev-workflow имеет spare-узлы OpenAI (переключение за 5 минут) | `services/ai-service/rag/workflow/book-rag-system-dev.json` |

**Рекомендация:** При росте нагрузки (>1000 AI-сессий/день) — инициировать ADR на Вариант C.

---

### R4. Стоимость эмбеддингов

**Что:** Gemini embeddings (3072 dims) стоит $0.00015 / 1K символов. При индексации 1000 книг × 5000 символов = 5M символов = $0.75 (разово). Но при обновлении каталога и добавлении новых книг — рекуррентная стоимость.

**Вероятность:** Средняя (рост каталога).

**Влияние:** Низкое для пилота, среднее при масштабировании.

**Митигации:**

| Митигация | Где |
| --- | --- |
| Индексация только при изменении книги (`book.updated` с diff) | `services/ai-service/internal/consumer/` |
| Кэш эмбеддингов: если метаданные не изменились — не переэмбедить | `services/ai-service/internal/ragstore/` |
| Batch-индексация (пачки по 100 книг раз в час) | Phase 2 |
| Fallback на OpenAI embeddings (dovetail с ADR-0002) | `services/ai-service/rag/scripts/swap-gemini-to-openai.py` |

---

### R5. 152-ФЗ (хранение данных в РФ)

**Что:** ФЗ-152 требует хранения персональных данных граждан РФ на территории РФ.

**Вероятность:** Высокая (целевой сегмент — РФ-библиотеки).

**Влияние:** Критическое — штрафы, блокировка.

**Митигации:**

| Митигация | Где |
| --- | --- |
| PostgreSQL в РФ (K8s-кластер в дата-центре РФ) | Phase 3 (деплой) |
| n8n self-hosted (не облачная версия) | Уже (`docker-compose.yml`, `library-n8n`) |
| Gemini API — данные уходят в Google (США) | **Риск!** Митигация: PII не уходит (см. R2), обезличенный текст. При ужесточении — замена на YandexGPT / T-Bank GigaChat. |
| Mailpit (email) self-hosted | `docker-compose.yml` (Phase 1) |

**Рекомендация:** Юридическая проверка до первого платящего клиента. При необходимости — ADR на локальный LLM.

### R6. Конфликт: `tenant_id` в Phase 1 vs существующие таблицы

**Что:** Решение Q5 — `tenant_id` во всех **новых** таблицах с Phase 1. Существующие таблицы (books, users, loans) получат `tenant_id` в Phase 3.

**Конфликт:** Если Phase 3 отодвинется, система будет в состоянии «одна БД на все библиотеки, но новые таблицы уже с tenant_id». Это inconsistency.

**Варианты:**

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| (A) Добавить `tenant_id` в существующие таблицы сразу | Консистентность | Изменение существующих миграций (checksum нарушен!) |
| (B) Оставить как есть (новые с tenant_id, старые без) | Не ломаем миграции | Временная inconsistency |

**Рекомендация:** (B). `pkg/migrate` хранит checksum — изменение существующей миграции сломает деплой. Phase 3 миграция (004_tenant.sql) добавит `tenant_id` в существующие таблицы + RLS. Это зафиксированный эпик.

---

### R7. Конфликт: clubs-db внутри user-service vs database-per-service

**Что:** Решение Q3 D — clubs-db управляется из user-service. Формально это нарушает «database-per-service» (один сервис = одна БД).

**Конфликт:** user-service будет иметь 2 DSN (user-db + clubs-db).

**Варианты:**

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| (A) Оставить как есть (clubs-db внутри user-service) | Нет нового сервиса, логическая близость к users | user-service шире, 2 DSN |
| (B) Вынести в отдельный club-service | Строгое database-per-service | Нарушает «без ADR — новых сервисов нельзя», +1 CI-джоба, +1 Dockerfile |

**Рекомендация:** (A). Формально: database-per-service соблюдается (у клубов своя БД). Процесс один, но это допустимое исключение для масштаба 5–20 библиотек. При росте (>50 библиотек, >100K постов/мес) — ADR на club-service.
